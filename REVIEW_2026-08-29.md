# Accaza Coffee House — Independent Code Review

**Date:** 2026-08-29
**Commit reviewed:** `04fd93f` (branch `arena/01a04ad6-accaza-sartoga`)
**Scope:** customer site, admin/POS, Accaza Books accounting, Firebase rules, Cloud Functions
**Method:** ran the project's own gates, read the source, and executed the real code where a claim needed proof.

---

## Verdict

**This is a seriously engineered system, not a hobby site.** The accounting core is the
strongest part of the codebase and is better than most commercial SMB POS products I have
seen. The weaknesses are concentrated in the frontend layer and in one security gap that
needs fixing before anything else.

| Area | Grade | Note |
|---|---|---|
| Accounting correctness | **A** | Double-entry enforced in code, not just tested |
| Server-side authority | **A−** | Pricing, approvals, ledger all server-owned |
| Test suite (logic) | **A−** | 31 hand-rolled checks, real domain assertions |
| Release/process discipline | **A−** | 9 ADRs, 14 release notes, honest gate output |
| Security | **C** | One verified admin-takeover XSS path; no CSP |
| Frontend performance | **C−** | 2.3 MB precached on every customer's phone |
| Code maintainability | **D+** | 574 KB single-file HTML, 4,265-char lines, no linter |

**Overall: B−.** The financial engine is production-grade. The shell around it is not.

## What is genuinely good

These are verified, not assumed.

**1. Double-entry integrity is enforced in the write path, not just in tests.**
`functions/lib/financial.js:15` defines `assertBalanced`, which throws above a 0.009
debit/credit gap. It is called from `movement()` at line 89 — the constructor every
financial movement passes through. There is no way to build an unbalanced ledger entry.

**2. Idempotency in `commitFinancial` is textbook** (`functions/index.js:1663`): existence
check → claim-token transaction → verify token → write → release claim on failure. Duplicate
replay is genuinely exactly-once, and the offline-sync test proves it.

**3. Pricing is server-authoritative and defended in depth.** `priceOrderLinesServer`
(line 1290) re-prices every line from the database menu, ignoring client numbers.
`createOnlineOrder` then compares against `expectedTotal` with a 0.01 tolerance and rejects
stale prices with a clear message. Layered on top: `enforceOrderRateLimit`, a SHA-256 order
signature used as an `orderLocks` idempotency key, per-line and per-order quantity caps, and
a total range check (`> 0 && <= 200000`).

**4. The financial data model is client-read-only.** I parsed `database.rules.json` and
checked all 23 nodes in `requiredProtectedNodes`: 22 carry `.write: false`. `.validate` rules
additionally freeze `refundAmount`, `voided`, `status`, `settlementStatus`, and `payoutId`
once written.

**5. The accounting tests are real.** `tests/financial-ledger-check.mjs` asserts
contra-revenue reclassification of platform discounts, GrabFood receivables at net-of-commission,
WHT/VAT splits, commission corrections, and full void reversals — then checks each movement
balances. This is domain-competent work, not coverage theatre.

**6. Browser and server costing engines are kept byte-identical** by an explicit gate
assertion (`assets/js/shared/costing.js` vs `functions/lib/costing.js`). That is an unusually
good safeguard against drift.

**7. Build markers are consistent.** I verified independently: `admin.html` meta = 357,
visible label `build&nbsp;v357`, manifest 357; `sw.js` `CACHE='accaza-v282'`, manifest 282.
All 49 `requiredFunctionExports` exist (71 exported in total).

**8. The project is honest about itself.** `release-manifest.json` says
`candidate_pending_production_verification` while the site is live on `accazacoffee.com`, and
the gate *prints* the four pending items rather than hiding them. That is rare.

## Findings

### P1 — Stored XSS in the print ticket ⇒ admin account takeover *(verified by execution)*

**`assets/js/admin/core.mjs:1411`** builds a kitchen ticket by concatenating order fields
straight into HTML, then **line 1449** writes it into a popup with `win.document.write(ticketHtml)`.

I extracted the actual shipped `window.printOrder` function out of the source text and ran it
in Node against a poisoned order:

```
document.write called: true
raw onerror payload present UNESCAPED: true
escaped instead (safe): false

...<span class="lbl">Address</span><span><img src=x onerror="alert(1)"></span>...
```

The chain closes:

1. `functions/index.js:1196` `textField()` only **trims and length-checks** — it does not
   strip or escape HTML. A customer's `notes` and `address` are stored verbatim.
2. Staff click **Print** on that order.
3. The payload executes in a same-origin popup under `admin.html`.
4. From there it can read the admin's Firebase session and take over the account —
   including the accounting side.

Two aggravating factors:

- **There is no CSP anywhere.** No `Content-Security-Policy` meta tag in `index.html`,
  `admin.html`, or `index-pos.html`, and none in `firebase.json` or `_config.yml`. Nothing
  blunts an injected script.
- The order *card* escapes correctly — `assets/js/admin/admin-orders.mjs:47` uses
  `escHtml(o.notes)`. Only the print path was missed.

**The fix is small.** `escHtml` is *already imported* at `assets/js/admin/core.mjs:13` and used
throughout that file. Three fields need wrapping in `printOrder`: `o.notes`, `o.address`,
`o.items`. Adding a CSP header would be worthwhile defence in depth.

### P2 — `functions/index.js` contains raw control bytes, so grep skips it

`functions/index.js:376` was meant to read `/[.#$/\[\]\x00-\x1f\x7f]/g`. The escape sequences
were written as **literal control characters** instead. Hex dump of that region:

```
5c 5b 5c 5d 00 2d 1f 7f 5d
\  [  \  ]  NUL -  US DEL ]
```

The regex still behaves correctly, so this is **not** a functional bug. But it makes the file
binary to `grep` and `ripgrep`. I hit this myself — my first search returned
`grep: functions/index.js: binary file matches` instead of results, and I had to re-run with
`-a` to see anything.

The consequence matters: **the single most security-critical file in the repo** — 3,132 lines
holding all financial authority — is silently skipped by default in any grep-based audit,
review, or CI scan. Fix by replacing the three raw bytes with the intended escape text.

### P3 — Every customer downloads the entire admin application

`sw.js` precaches 55 assets on `install`. I measured them against the repo:

```
precached assets present: 54 / 55      ('/' has no file — harmless)
total precache bytes:     2283 KB
  of which /assets/js/admin/**: 1026 KB
```

`assets/js/pwa-register.js` is loaded by `index.html` and calls
`navigator.serviceWorker.register('/sw.js',{scope:'/'})` on `load`. So **a customer browsing
the coffee menu on mobile pulls ~2.3 MB**, including `pos.js`, `analytics.js`, `finance.js`,
`register.js`, and `staff-access.js`. On Philippine mobile data that is a real cost and a
real wait.

Also precached: `favicon_512x512.png` at **238 KB** for a favicon.

Measured page weights (this dev server does not compress; GitHub Pages does):

| Page | Raw | Gzipped |
|---|---|---|
| `/` (customer landing) | 230 KB | **112 KB** |
| `/admin.html` | 310 KB | 126 KB |
| `/index-pos.html` | 574 KB | 190 KB |
| `/books.html` | 161 KB | 43 KB |

A 112 KB gzipped HTML document for a landing page is heavy — 52 KB of it is inline CSS.

**Fix:** split the precache list into a customer shell and an admin shell, and register the
admin list only on `admin.html`. `pwa-register.js` already has an `isAdmin()` helper.

### P4 — `index-pos.html` was retired in `.gitignore`, but the retirement never took effect

The team already decided this page should go. `.gitignore:34` lists it under a header that
could not be clearer:

```
# Retired/manual source copies — use Git history instead
admin-backup.html
index backup*.html
index-pos.html
Firebase rules - backup.txt
```

**The rule does not work, because the file is still tracked.** Git ignore rules have no effect
on paths already in the index. Verified:

```
$ git check-ignore -v --no-index index-pos.html
.gitignore:34:index-pos.html      # the rule matches the path

$ git check-ignore -v index-pos.html
(no output)                        # not ignored — because it is tracked

$ git ls-files -i -c --exclude-standard
index-pos.html                     # tracked files matching an ignore rule: exactly one

$ git cat-file -s HEAD:index-pos.html
574485                             # committed in HEAD at full size
```

So a 574 KB page the team believes is retired is still in the repository and still published.
The other three patterns in that block are genuinely retired — `index-pos.html` is the only
tracked-but-ignored file. Retiring it for real needs `git rm --cached index-pos.html`.

It is also functionally orphaned: `grep -rln 'index-pos'` across every `.html`, `.js`, `.mjs`,
and `.json` returns **zero matches**. It is not in `sw.js`'s `ASSETS`, not in
`release-manifest.json`'s `authoritativeFiles`, and nothing links to it — yet it serves
HTTP 200 at `/index-pos.html`.

It contains 292 KB of inline JavaScript and 4,845 lines, and is the only page with
accessibility regressions: **7 `<img>` tags missing `alt`** (the e2e suite only covers
`index.html`, which is clean — 20 images, 0 missing alt, 0 placeholder links).

If it must stay, it belongs in `release-manifest.json` like every other authoritative file.

### P5 — The release gate's "protected nodes" check does not check protection

`tests/release-readiness-check.mjs`:

```js
for(const node of manifest.requiredProtectedNodes){
  if(!rules.includes(`"${node}"`))fail(`Required protected database node missing: ${node}`);
}
```

That is a **string-presence** test. A node passes if its name appears anywhere in the rules
file, regardless of whether anything is actually protected. Only a separate hard-coded list
of 7 nodes gets the real `.write === false` assertion.

Result: `activeOrders` is declared in `requiredProtectedNodes` but its rule grants admins
`.write` (I checked — it is not `false`). Practical exposure is low, since no client code
writes `activeOrders` (`grep` for client writes returns nothing; the server maintains it via
`syncActiveOrderProjection`). But 16 of the 23 "protected" nodes are only name-checked, and
the gate reports PASS.

### P6 — One role predicate is copy-pasted 107 times

```
full 9-clause admin role predicate repeated: 107 times
approx bytes consumed:                       ~49 KB of the 94 KB rules file (52%)
```

Firebase Realtime Database rules have no macro support, so some repetition is expected — but
107 copies of a 9-branch disjunction means a role change is a 107-site edit. This file should
be generated from a template with a checked-in diff, not hand-maintained.

The same disease shows up in line lengths:

```
4265 chars  functions/index.js:2217
3089 chars  functions/index.js:2022
2707 chars  database.rules.json:23
2412 chars  assets/js/admin/pos.js:1018
```

### P7 — No linter, no formatter, no type checker

No `.eslintrc`, `prettier`, `.editorconfig`, `tsconfig`, `biome`, or `husky` anywhere in the
repo. The test suite is strong, but it is 31 hand-rolled `assert()` scripts rather than a
framework, so there is no watch mode, no coverage, and no isolation.

Combined with the single-file HTML apps (`index-pos.html` 574 KB / 292 KB inline JS,
`books.html` 149 KB inline JS), a change to one line of POS logic ships as a 574 KB
cache-busting document.

### P8 — 16 copies of the escape helper, in two incompatible variants

I extracted and functionally tested every `esc`/`escHtml` definition:

- **9 files** escape only `& < > "` — no single quote:
  `analytics.js`, `channel-pricing.js`, `finance.js`, `admin/packages.js`, `pos.js`,
  `register.js`, `staff-access.js`, `undeposited.js`, `customer/packages.js`
- **7 files** escape `& < > " '` correctly:
  `form-dialog.js`, `operations-dashboard.js`, `overview-command.mjs`, `sales-history.js`,
  `shared-ui.mjs`, `staff-inbox.js`, `customer/core.mjs`

The 4-char variants are unsafe whenever a value lands in a single-quoted HTML attribute.
`shared-ui.mjs` already exports a correct `escHtml` — the other 15 copies should import it.

*Correction to an earlier read of mine: I suspected `channel-pricing.js` had a malformed
escaper. I ran it — it handles `& < > "` correctly and passes backslash and single-quote
through unchanged. It is merely in the 4-char group, not broken.*

### P9 — Money is float, with two different balance tolerances

Money is stored as `Math.round(x*100)/100` in `financial.js`, `books-bridge.js` (`r2`), and
`costing.js`. That is defensible for PHP amounts.

The sharper issue is that "is this balanced" has **two different answers**:

- `Financial.assertBalanced` → `> 0.009` throws
- `BooksBridge.linesBalanced` → `< 0.005` is balanced

A movement can satisfy one and fail the other. `books-bridge.js` also uses `0.009` in one
place (line 166) and `0.005` in three others. These should be one exported constant.

### P10 — Production verification is self-declared pending

`release-manifest.json` status is `candidate_pending_production_verification`, with four
pending items: `productionPerformanceReview`, `backupRestoreTest`,
`quarterlyPermissionReview`, `quarterlyDependencyReview`. The `CNAME` points at a live
domain.

To the team's credit the gate prints this rather than hiding it. But `backupRestoreTest`
being pending on a system that holds a business's general ledger is the one I would not
leave open.

## Corrections to my own process

Two of my own probes produced wrong answers, and I am recording them so the findings above
can be trusted:

1. My first XSS scan looked only for `${...}` template interpolation and reported **0
   findings**. This codebase builds HTML with `'...' + value + '...'` concatenation, so the
   scanner never matched. A second, concatenation-aware pass reported **193** — but on
   inspection many were parser artifacts from ternaries inside template strings. Neither
   number is meaningful. The real finding (P1) came from targeted reading of the print path
   and was then **confirmed by executing the shipped function**, not by counting.
2. I initially reported `functions/index.js` as "binary" without knowing why. It is a
   2-line regex issue (P2), not corruption — and the regex still works.
3. My first pass on `index-pos.html` stopped at "zero references, so it is either dead weight
   or an unmanaged live page." I had not read `.gitignore`, which shows the team had already
   retired it — and that the retirement silently failed. The accurate finding (P4) is
   stronger than my first guess, and only showed up after checking tracking status.

## Recommended order of work

1. **P1** — escape `o.notes`, `o.address`, `o.items` in `printOrder`. ~3 lines, `escHtml` is
   already imported. Add a CSP header as defence in depth.
2. **P2** — restore `\x00-\x1f\x7f` as escape text so the Functions file is greppable.
3. **P3** — split the service-worker precache into customer and admin shells.
4. **P4** — `git rm --cached index-pos.html`. The `.gitignore` rule at line 34 already says
   this page is retired; it just cannot take effect while the file is tracked.
5. **P10** — run and record the backup/restore test.
6. **P5, P8, P9** — tighten the gate assertion, collapse the escapers, unify the tolerance.
7. **P6, P7** — generate the rules file from a template; add ESLint + Prettier.

Items 1–4 are a day's work and remove nearly all of the acute risk.
