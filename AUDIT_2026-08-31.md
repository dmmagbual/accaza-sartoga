## Verdict — B+

The engine is production-grade; the perimeter has two switches left in the wrong position.

The accounting core, server-authority model, and release discipline are genuinely strong — better than most commercial SMB POS. The Aug-29 critical (print-path XSS) is **fixed and holding** in v409, page weight is dramatically improved, and there is **no open critical**. What remains is concentrated and cheap to close: App Check is built but **not enforced**, there is still **no CSP**, backups are taken but the **restore has never been drilled**, and every customer still downloads the entire admin app.

## Findings

Every finding cites a file you can open. Severity is by current build.

### H-1 — App Check is built and running, but not enforced *(High, Open)*
Client initialises App Check (reCAPTCHA Enterprise) and `createOnlineOrder` logs `appCheck: Boolean(request.app)` per order — tokens flow and are observable — but the server flag is off, so requests without a valid token are **not rejected**. Monitor mode, not enforce.
- `functions/.env.accaza-sartoga` → `ENFORCE_APP_CHECK=false`
- `functions/index.js:497`; `src/customer/core/00-firebase-auth.mjs:11`; `src/functions/30-orders.js:323`

**Impact:** customers auth anonymously, so `auth != null` is trivially met by any script. Order creation is defended only by rate-limit + SHA-256 signature + quantity/total caps — solid vs. accidental replay, weaker vs. a determined bot. Highest-leverage security switch available.
**Fix:** use the token-presence telemetry you already log to confirm real traffic sends valid tokens, then flip `ENFORCE_APP_CHECK=true` staged (order callables first, watch rejections, then the rest). Also confirm App Check enforcement on the Realtime Database in the Firebase console (separate toggle).

### H-2 — Backups are validated but never restore-drilled, and sit in one project *(High, Open — was P10)*
`backupDatabaseDaily` runs 03:00 Manila, builds a SHA-256 envelope, validates before upload, 30-day retention, records to `/systemHealth/backups/latest`. Two gaps:
1. `release-manifest.json → backupRestoreTest: pending` — the restore path has never been exercised.
2. Backups write to the **same project's** Storage bucket (`PROOF_BUCKET`) — ledger and backups share one blast radius.

**Impact:** a backup you've never restored is a hope, not a capability — and the first restore should not be during an outage on a system holding the GL. If the project/account is compromised, suspended, or fat-fingered, backups go with it.
**Fix:** restore the latest envelope into a staging project, reconcile the ledger, record the evidence (closes `backupRestoreTest`). Add one **off-project** copy and keep at least one restore-tested copy outside `accaza-sartoga`.

### M-1 — No Content-Security-Policy anywhere *(Medium, Open since P1)*
No CSP in `index.html`, `admin.html`, `books.html`, or site config. Recommended Aug-29 as defence-in-depth; the XSS was patched but the CSP never landed.
**Impact:** the print-path injection is closed, but escaping is duplicated across 16 helper copies (two cover only 4 of 5 metacharacters). A CSP is the backstop that turns the next missed-escape into a blocked script rather than an admin-origin takeover.
**Fix:** strict CSP (`script-src` self + the gstatic Firebase CDN; no `unsafe-inline` for scripts). GitHub Pages can't set headers → ship as `<meta http-equiv>` or serve shells via a Function/CDN. Do `admin.html` first.

### M-2 — The most security-critical file is invisible to grep *(Medium, Open since P2)*
`functions/index.js` (3,694 lines, all financial authority) still contains three raw control bytes; the OS classifies it as binary `data`, so grep/ripgrep skip it by default.
- `file functions/index.js` → `data`
**Impact:** not a runtime bug — the regex works — but every default search, secret-scan, and reviewer silently skips the file that most needs review.
**Fix:** replace the raw bytes with the intended escape text `\x00-\x1f\x7f`. One line, no behaviour change.

### M-3 — Clearing/suspense accounts have no standing-balance alarm *(Medium, Open)*
`auditFinancialControls` reconciles each order's Admin net sales vs. its Finance movement (`sale_not_posted`, `sale_amount_mismatch`, `unmapped_payment_method`) — good per-transaction control. Nothing watches the **standing residual** in clearing/suspense accounts: 1290 Inventory Receiving Clearing, 1900, 5090, 2090, 1190, and 5905 Inventory Reconciliation.
**Impact:** your own handover shows 5905 at ₱−715.83 "needs review", caught by eye not alert. Clearing accounts should trend to zero; a lingering residual is exactly what "every number has evidence" is meant to surface.
**Fix:** scheduled control that reads each clearing/suspense balance and flags an exception above a small threshold (e.g. ₱50) or aged past N days; route to the existing exception surface.

### M-4 — Two different definitions of "balanced" *(Medium, Open since P9)*
- `functions/lib/financial.js:17` → throws when |debit−credit| > **0.009**
- `functions/lib/books-bridge.js:233` → balanced when |dr−cr| < **0.005** (and 0.009 at line 177)

**Impact:** a movement can pass one and fail the other in the 0.005–0.009 band — the kind of inconsistency that produces an untraceable ₱0.01 phantom.
**Fix:** export one `BALANCE_EPSILON` (use 0.005 for centavo precision) and import in both engines.

### M-5 — Seven moderate vulnerabilities in Functions dependencies *(Medium, Open)*
Root deps clean (0). `functions/` (production server code) → `npm audit --omit=dev` reports 7 moderate advisories; `quarterlyDependencyReview` is still pending.
**Fix:** review advisories, `npm audit fix` where non-breaking, record the review, and wire the existing `audit:dependencies` script into the quality gate.

### M-6 — Every customer downloads the entire admin + books app *(Medium, Open since P3)*
Service worker (`accaza-v370`) precaches one flat list including `pos.js`, `finance.js`, `register.js`, `analytics.js`, `staff-access.js`, and the books bundles. A customer opening the menu on mobile pulls the whole back office.
**Impact:** wasted mobile data + slower first visit — a real cost on PH mobile and the first impression for a walk-in. (Not a data-exposure issue — client JS is public regardless — bandwidth/speed.)
**Fix:** split precache into customer shell vs admin shell; register the admin list only from `admin.html` via the existing `isAdmin()` in `pwa-register.js`. Also drop/optimise the 238 KB `favicon_512x512.png` in the precache.

### L-1 — Financial-control checks are pull-based, not pushed *(Low, Open)*
Control logic exists (`auditFinancialControls`, `alert-escalation.js`, `production-health.js`) but runs on demand/at certification. No outbound alert channel found wired to fire on a **critical** control break — it surfaces in-dashboard only if someone opens it. Push/email plumbing exists elsewhere (staff push, contact SMTP) but isn't connected to financial-control breaches.
**Fix:** schedule `auditFinancialControls` (hourly + at close) and push/email you on any `severity: critical`.

### L-2 — Release gate checks node names, not node protection *(Low, Open since P5)*
The "required protected nodes" test passes on name-presence, not real `.write === false`. `activeOrders` is listed protected but is admin-writable (low practical risk — no client writes it).
**Fix:** assert the resolved `.write` equals `false` per protected node in `tests/release-readiness-check.mjs`.

### L-3 — Deploy uses the deprecated `FIREBASE_TOKEN` *(Low, Advisory)*
Both workflows deploy with a long-lived CI token; Google has deprecated it in favour of service-account / Workload Identity Federation.
**Fix:** migrate to a scoped service account via GitHub OIDC/WIF — no standing long-lived credential.

### L-4 — Release manifest still "candidate pending verification" *(Low, Open since P10)*
Four open evidence items: production performance review, backup restore test, quarterly permission review, quarterly dependency review. The gate prints this honestly (a strength), but the site is live — close them to reach a true "verified".
**Fix:** H-2 and M-5 close two; the other two are ~an afternoon each (real-device performance pass; documented admin-role/permission review).

### L-5 — No linter, formatter, or type-checker *(Low, Open since P7)*
No ESLint/Prettier/editorconfig/tsconfig. The 50+ hand-rolled suites largely compensate; no automated guard on style drift or the escaper-variant divergence (M-1). Two parallel trees (`src/` authored, `assets/js/` bundled) are kept honest by a drift test — acceptable but doubles reviewer surface.
**Fix:** add ESLint + Prettier to the gate. Lowest priority — the tests carry the weight.

## What's genuinely strong (verified, not assumed)

- **Double-entry enforced in code** — `assertBalanced` throws above ₱0.009 in the constructor every movement passes through. Unbalanced entries are structurally impossible, not just tested.
- **Immutable, source-linked ledger** — `financialMovements` is `.write:false` to all clients; corrections reverse-and-repost preserving original ID + audit history (verified on the recent legacy Other-Income reclassification).
- **Textbook idempotency** — existence check → claim-token txn → verify → write → release-on-failure; offline POS replay is exactly-once and tested.
- **Server-authoritative pricing** — every online line re-priced from the DB menu server-side, checked vs. client total, stale prices rejected; layered with rate-limit, signature, and caps.
- **Real RBAC + segregation of duties** — 8 portal roles with granular `adminPerms`; a financial-impact incident cannot be resolved by its creator.
- **Storage locked server-only** — `storage.rules` is `allow read, write: if false`; payment proofs validated by magic-bytes server-side.
- **XSS fixed & regression-guarded** — v409 `printOrder` wraps all 10 customer fields; executable test runs the real shipped function against a poisoned order.
- **Honest release engineering** — full suite gates every deploy; manifest says "pending verification" while live rather than faking green.
- **Validated automated backups** — daily, SHA-256-sealed, integrity-checked, 30-day retention. Mechanism is right; needs a restore drill + off-site copy (H-2).
